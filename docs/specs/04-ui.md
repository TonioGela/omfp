# 04 — UI (TypeScript)

The UI is a TypeScript web app (D-18): React 19 with React Aria Components (S-11), styled by our own token CSS,
bundled and tested with Bun, in the `ui/` workspace. The same bundle runs in the browser, served by the daemon
(DMN-008), and from M7 in the Tauri desktop window: same components, same state handling.

## Platforms

| | Web | Desktop (M7) |
| --- | --- | --- |
| Runtime | the release bundle (`just build-web`) in the browser | the same bundle in a Tauri 2 webview (the system webview, WebKitGTK on Linux) |
| Daemon | remote/local `omfp daemon`, which also serves the static bundle | the local daemon of the data directory, found or started in the background by `omfp desktop` (ARC-003) |
| WebSocket client | `@omfp/client` over the browser's `WebSocket` | the same |
| Token | entered once, or read from the URL fragment `#token=…` printed by `omfp daemon`; kept in `localStorage` | read from the data directory by `omfp desktop` and handed to the window at launch |

| ID | Requirement |
| --- | --- |
| UI-001 | The UI MUST have a single WebSocket transport (`@omfp/client` over the standard `WebSocket` API) for web and desktop, and it MUST pass the transport test suite against a real daemon (TST-030). |
| UI-002 | On web, after reading `#token=…` the UI MUST remove the fragment from the address bar (`history.replaceState`). |
| UI-003 | On connection loss the UI MUST show a non-blocking banner, reconnect with exponential backoff (max 10 s), and resubscribe each topic with its last `{epoch, seq}` (PRT-020). |
| UI-004 | The desktop build MUST keep the daemon reachable on `127.0.0.1` with its token, so a browser can attach to the same daemon (ARC-004). |
| UI-005 | Every `omfp desktop` invocation MUST open a new window on the shared local daemon (D-16). Window-local state (selected thread, open panels, layout, drafts) MUST stay per window; everything else comes from the daemon, so all windows show the same threads. |

## State and code structure

The UI is a Bun workspace of small packages. The protocol client has no UI dependency, so it is tested against a real
daemon and can serve other clients (scripts, agents, the desktop shell):

```text
ui/packages/
  protocol/      @omfp/protocol: protocol types and method table generated from the daemon's JSON Schemas
                 (`just gen-ts`), envelope, topics
  core/          @omfp/core: the omfp-core reducer ported to TypeScript, checked against the Rust reducer's golden
                 states (D-04)
  client/        @omfp/client: transport (WebSocket); session (hello, request/response correlation, subscriptions
                 with {epoch, seq}, reconnect with backoff, resubscribe, resync); model (connection status, index
                 with repositories, workspaces, threads and theme, per-thread ThreadState, change notifications)
  kit/           @omfp/kit: React Aria Components wrappers styled by token CSS (tokens.css, kit.css)
  app/           @omfp/app: the web app; build.ts makes the release bundle in dist/
    src/sdk/       the widget SDK (seed of M4's `omfp` SDK): host, frame store (one snapshot per animation frame),
                   window store (window-local state), commands, hooks over the client model
    src/vm/        pure view-model functions: ThreadState / DTOs → display data (unit tested, no DOM)
    src/widgets/   the built-in `omfp:*` widgets (thin: render vm output, call the SDK)
    src/frame/     the frame outside the view: connection banner, view switcher, `:` command line, safety net for
                   pending interactions, notifications, live region
    src/view/      views: layout tree (`row`/`col`/`tabs`/`stack` of widget refs with props, the `views.json` shape
                   of 08) rendered from the widget registry (see UI-024)
    src/keymap/    keymap as data: key sequence → command id, per mode
    src/theme/     built-in light/dark, user theme from the daemon, color scheme and density
    src/strings/   all UI text
```

| ID | Requirement |
| --- | --- |
| UI-010 | Thread state MUST come only from the `omfp-core` reducer (ARC-006). UI-only state (scroll position, expanded cards, composer draft) lives beside it and is never sent to the daemon. |
| UI-011 | Display logic (grouping, labels, status badges, tool-card summaries, diff stats) MUST live in `ui/packages/app/src/vm/` as pure TypeScript functions, so it can be tested without a DOM (TDD at unit level). |
| UI-012 | Model updates from streaming events MUST be coalesced to at most one render per animation frame. |

## Layout

Threads are the primary list; each lives in a workspace (a folder, D-11), and the workspace's repositories are always
visible next to the thread. Repositories are never parents of threads.

```text
┌──────────────────┬───────────────────────────────────────────┬────────────────┐
│ Threads          │ Thread header: title · tags · workspace   │ Panels (tabs)  │
│ group: [ws ▾]    │ chip · repo chips (name, kind, branch) ·  │  Workspace     │
│ filter: tag/…    │ model · thinking · context % · cost ·     │   checkout-v2  │
│ ▾ checkout-v2    │ state                                     │   ↪ frontend   │
│   ● implement    │───────────────────────────────────────────│   ⑂ fe-v2      │
│   ◐ review       │ Transcript (virtualized)                  │   ⬇ backend    │
│ ▾ scratch        │   user / assistant / tool cards / notices │   + add repo   │
│   ! questions    │   pending interactions (approval, ask)    │  Changes       │
│                  │───────────────────────────────────────────│  Subagents     │
│ + thread         │ Queue chips · Composer (/ commands, imgs) │  Todos · Tree  │
└──────────────────┴───────────────────────────────────────────┴────────────────┘
```

| ID | Requirement |
| --- | --- |
| UI-020 | The sidebar MUST list threads with their process state and attention state (running, awaiting input, failed, idle, unread) and their workspace name. |
| UI-021 | Threads awaiting input MUST be reachable with one keyboard shortcut ("next thread needing attention"). |
| UI-022 | The thread list MUST support grouping (workspace — the default —, none, tag, repository, PR) and filtering by the same keys plus free text; grouping by repository shows a thread under each repository its workspace contains. |
| UI-023 | Creating a thread MUST ask only for a workspace — a new one (optional name and existing folder to use) or an existing one —, optionally repositories to add right away (link a folder or a known repository, new worktree of a repository, clone a URL; PR after S-08) and the first message, all in one dialog; there is no title field (DMN-073). The header offers rename; asking the agent to rename the thread works through its `set_thread_title` tool. |
| UI-024 | Panels MUST go through a registry (kind, typed content, placement: side, bottom, main, floating) rather than a fixed layout, so new panel kinds — including views published by agents ([08](08-agent-control.md)) — fit without restructuring the shell. |
| UI-025 | A **Workspace** panel MUST show the selected thread's workspace: name (editable), folder path, its threads, and every repository discovered in it with kind (link and target, worktree and its main repository, clone), branch, dirty state and ahead/behind, updated live as the agent adds or removes repos; actions add (link, known repository, new worktree, clone) and remove (DMN-025, with a confirmation for anything but a link), rescan, and a badge when the same repository is in another workspace with live threads (DMN-027). A list of all workspaces (threads count, open, remove) and of known repositories (add, remove; "add to this workspace") is reachable from it. |
| UI-026 | The thread header MUST offer archive (unarchive when archived) and delete; delete asks for confirmation in a dialog saying the thread's history is removed and its workspace is kept. Archived threads are hidden everywhere except the sidebar's **Archived** filter, which lists only them so they can be reopened, unarchived or deleted. Archiving or deleting the selected thread clears the selection and drops its draft. |

### Transcript

| ID | Requirement |
| --- | --- |
| UI-040 | Assistant text MUST render as Markdown (react-markdown with remark-gfm, without rehype-raw): raw HTML from the model is never turned into DOM, so it never executes. Beyond that, no extra hardening (full-access use, D-17): remote images load and CSS classes are kept. |

### Tool cards

omp sends raw events (`tool_execution_start/update/end` with arguments and result); cards are our job.

| Tool | Card |
| --- | --- |
| any (fallback) | name, one-line argument summary, status, duration; expandable pretty JSON args and text result |
| `bash` | command, streaming output (ANSI → HTML), exit code, and the workspace it ran in when not the cwd |
| `read` | path and line range, result collapsed |
| `edit` / `write` | file path (relative to its workspace, with the workspace chip) and a diff view |
| `grep` / `glob` / `find` / `ast_grep` | query and result list with file links |
| `task` | subagent name and task, live progress, link to the subagent panel |
| `todo` | checklist |
| `web_search` / `fetch` | query, link list |
| `ask` | questions with the given answers |

| ID | Requirement |
| --- | --- |
| UI-050 | Every tool MUST render through the fallback card when no specialized renderer exists; specialized renderers are added one at a time, each with tests (TST-020). |
| UI-051 | Tool argument/result shapes for specialized cards MUST be captured as fixtures from the pinned omp (recorded by the contract tests, TST-012) and re-checked on every omp upgrade. |
| UI-052 | Cards MUST be collapsible; failed tools (`isError`) MUST be visually distinct and expanded by default. |

## Rendering details

| ID | Requirement |
| --- | --- |
| UI-090 | Code highlighting MUST work on both platforms. The library is chosen by spike S-03 with a bundle size budget (target: total gzipped bundle ≤ 3 MiB). |
| UI-091 | Styling uses plain CSS driven only by design tokens (CSS custom properties named after Material 3 roles: `--omfp-primary`, `--omfp-on-primary`, `--omfp-surface`, `--omfp-surface-container`, `--omfp-outline`, …, plus radius, spacing, font and density tokens); the shell, the kit and widgets never hard-code colors. The theme is **global** to omfp and **kept by the daemon** (a setting, served at `/theme.css`, change pushed to every window), because the daemon may be remote: built-in light and dark follow `prefers-color-scheme` with a manual override; a user theme (CSS overriding any token) replaces them. It can be set with `theme.set`, by `omfp theme set <file>` (local or `--daemon <url>`), by a theme file on the daemon host (`$XDG_CONFIG_HOME/omfp/theme.css`, watched), and by the desktop app (M7), which watches the same path **on the client machine** and pushes it — so **matugen** (template in `contrib/matugen/`) recolors every window live even with a remote daemon. |
| UI-092 | All interactive elements MUST be keyboard reachable, dialogs MUST trap focus, and status changes MUST be announced through an ARIA live region. |
| UI-093 | From M3 (D-18) the UI is TypeScript with React 19 (S-11) and React Aria Components for behaviour and accessibility (UI-092), styled by our own token CSS; a thin kit (`omfp/kit`: card, button, tabs, table, list, progress, log, diff, markdown, …) wraps them for the shell and for widgets. |
| UI-094 | Fonts are tokens too (`--omfp-font-prose`, `--omfp-font-ui`, `--omfp-font-code`), defaulting to the system families (`ui-serif`, `system-ui`, `ui-monospace` with fallbacks): serif only for message prose (transcript text, Markdown), sans for the interface, monospace only for code (code blocks, inline code, tool commands and output). Choosing other fonts is left to the theme for now. The layout is dense by default, with a density token (compact / normal) settable at run time. |
| UI-095 | Keyboard handling MUST go through one keymap (data: key sequence → command id, per mode), so bindings can be made configurable later. Default bindings are vim-style: `j`/`k` move between threads or messages, `gg`/`G` top/bottom, `Ctrl-d`/`Ctrl-u` half pages, `/` search, `i` focuses the composer, `Esc` leaves it; `:` opens a command line that is also the command palette (`:new`, `:archive`, `:theme dark`, … with completion); `Space` is the leader for actions. The transcript handles PageUp/PageDown/Home/End itself (WebKitGTK does not scroll a focused container, S-11). Modal (Helix-style) editing inside the composer is out of scope for M3. |
| UI-096 | When a thread starts needing the user (approval, `ask`, failure) or finishes a turn and the window does not have focus, the UI MUST show a system notification (Notification API, permission asked on a user gesture); clicking it focuses the window on that thread. Nothing is shown while the window has focus. |
| UI-097 | UI settings come from the daemon (DMN-009): `[ui]` `density` (compact / normal), `notifications` (background / always / never), `fonts` (`prose`, `ui`, `code` overriding the font tokens), and `[keymap]` entries (key sequence → command id) that override the default bindings one by one. Changes apply live in every window; `:set <key>=<value>` changes a setting through `settings.set`. |
