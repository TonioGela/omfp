# 04 — UI (TypeScript)

The UI is a TypeScript web app (D-18): React 19 with React Aria Components (S-11), styled by our own token CSS,
bundled and tested with Bun, in the `ui/` workspace. The same bundle runs in the browser, served by the daemon
(DMN-008), and from M7 in the Tauri desktop window: same components, same state handling.

## Platforms

| | Web | Desktop (M7) |
| --- | --- | --- |
| Runtime | the release bundle (`just build-web`) in the browser | the same bundle in a Tauri 2 webview (the system webview: WebKitGTK on Linux, WKWebView on macOS from M11) |
| Daemon | remote/local `omfp daemon`, which also serves the static bundle | the local daemon of the data directory, found or started in the background by `omfp desktop` (ARC-003) |
| WebSocket client | `@omfp/client` over the browser's `WebSocket` | the same |
| Token | entered once, or read from the URL fragment `#token=…` printed by `omfp daemon`; kept in `localStorage` | read from the data directory by `omfp desktop` and handed to the window at launch |

### macOS (M11)

The desktop window on macOS is the same Tauri 2 window on the system's WKWebView (S-15); the daemon's tray is a menu
bar item (DMN-171). The platform differences:

| ID | Requirement |
| --- | --- |
| UI-250 | (M11) **Window storage on macOS**: WKWebView ignores a data directory, so the window MUST take a `WKWebsiteDataStore` identifier per data directory (UI-005): 16 random bytes made on first use and kept in `<data dir>/webview/store-id` (replaced when not 16 bytes), so two daemons never share the window's `localStorage` (macOS 14 or later). |
| UI-251 | (M11) **Microphone on macOS**: the binary MUST embed an Info.plist (`__TEXT,__info_plist`: bundle id `dev.omfp.desktop`, `NSMicrophoneUsageDescription`, `LSMinimumSystemVersion` 14.0), without which WKWebView hides `navigator.mediaDevices`; the window MUST grant WKWebView's microphone requests (unhandled, WebKit asks on every page load), so macOS asks the user once per app (TCC: the app's signature, so again after a rebuild while the bundle is ad-hoc signed, ENV-041). WKWebView has WebRTC, so live voice takes `thread.live_connect` there like a browser (UI-188). |
| UI-252 | (M11) **Notifications on macOS**: WKWebView denies web notifications, and the window has no IPC, so the window MUST give the page its own `Notification` (an initialization script, before the page's scripts): `permission` `granted`, and each `new Notification(title, { body, tag })` a navigation of a hidden frame to `omfp-notify:?title=…&body=…&tag=…`, which the window cancels and posts to macOS's notification center as `dev.omfp.desktop` (`NSUserNotificationCenter`: its successor needs an app bundle around the running executable; a notification with the same tag replaces the last one). The page's routing is unchanged (UI-096, UI-192: a system notification while the window has no focus). macOS asks once whether `omfp` may show notifications (until allowed, they only reach the Notification Center's storage); a click does not select the thread (no delegate without `unsafe`). Linux keeps WebKitGTK's own notifications. |
| UI-253 | (M11) **Color scheme on macOS**: the window MUST follow the system appearance through AppKit (WKWebView maps the window's effective appearance to `prefers-color-scheme`); the settings-portal follower of UI-195 is Linux only. |
| UI-254 | (M11) **Menu bar item**: on macOS the tray of UI-217..UI-219 MUST be an `NSStatusItem` with the same menu model: a click opens the menu (the macOS convention; no left-click New window), labels without the `_` doubling, the tooltip the status line; the idle icon is a template image (the π's alpha, tinted by macOS for a light or dark menu bar), running and needs-you keep their coloured dots. **Open in browser** runs `/usr/bin/open <url#token>`. |
| UI-280 | (M11) **Key chips on macOS**: where `navigator.platform` starts with `Mac` (browsers and the desktop window's WKWebView), the key chips of UI-148 and the `:help` panel (UI-198) MUST label the Alt modifier `opt` (`opt+a`, `opt+enter`), the macOS key's name; the bindings stay `Alt-…` and every other label (and Linux) is unchanged. |
| UI-281 | (M11) **Zoom on macOS**: the desktop window's View menu MUST hold Actual Size (Cmd-0), Zoom In (Cmd-=) and Zoom Out (Cmd--) atop Tauri's default items, which set the webview's page zoom through the browsers' steps (50, 67, 75, 80, 90, 100, 110, 125, 150, 175, 200, 250, 300 %; the ends stay, a level between two steps goes to the next). No key of the keymap uses Cmd. Linux has no such keys: Tauri's zoom hotkeys are a page script calling the window over IPC, which the window does not have (S-04), and WebKitGTK windows have no menu. |
| UI-282 | (M11) **New window on macOS**: the desktop window's File menu MUST start with New Window (Cmd-N), which starts one more `omfp desktop` detached — `--data-dir` of this window, `--connect` and `--token` when this window got them, not its `--thread` — like the menu bar's New window (UI-218, UI-254). Linux has no such key: without a menu the page would have to send it, and Ctrl-n is the file editor's vim key (UI-111). |

## State and code structure

The UI is a Bun workspace of small packages. The protocol client has no UI dependency, so it is tested against a real
daemon and can serve other clients (scripts, agents, the desktop shell):

```text
ui/packages/
  protocol/      @omfp/protocol: protocol types and method table generated from the daemon's JSON Schemas
                 (`just gen-ts`), envelope, topics
  core/          @omfp/core: the omfp-core reducer ported to TypeScript, checked against the Rust reducer's golden
                 states (D-04)
  client/        @omfp/client: transport (WebSocket); session (hello, request/response correlation, subscriptions
                 with {epoch, seq}, reconnect with backoff, resubscribe, resync); model (connection status, index
                 with repositories, workspaces, threads and theme, per-thread ThreadState, change notifications)
  kit/           @omfp/kit: React Aria Components wrappers styled by token CSS (tokens.css, kit.css)
  app/           @omfp/app: the web app; build.ts makes the release bundle in dist/ (with the import map that
                 widgets resolve `react`, `omfp/sdk` and `omfp/kit` through, AGT-012)
    src/sdk/       the widget SDK, `omfp/sdk` (AGT-016): host, frame store (one snapshot per animation frame),
                   window store (window-local state), commands, hooks over the client model, widget hooks
    src/vm/        pure view-model functions: ThreadState / DTOs → display data (unit tested, no DOM)
    src/widgets/   the built-in `omfp:*` widgets (thin: render vm output, call the SDK), each folder written like an
                   agent widget so it can be copied (AGT-021)
    src/frame/     the frame outside the view: left column, connection banner, view switcher, layout editing
                   controls, `:` command line, safety net for pending interactions, notifications, live region
    src/view/      views: layout tree (`row`/`col`/`tabs`/`stack` of widget refs with props, the `views.json` shape
                   of 08) rendered from the widget registry (see UI-024), the widget loader and the layout edits
    src/keymap/    keymap as data: key sequence → command id, per mode
    src/theme/     built-in light/dark, user theme from the daemon, color scheme and density
    src/strings/   all UI text
```

| ID | Requirement |
| --- | --- |
| UI-010 | Thread state MUST come only from the `omfp-core` reducer (ARC-006). UI-only state (scroll position, expanded cards, composer draft) lives beside it and is never sent to the daemon. |
| UI-011 | Display logic (grouping, labels, status badges, tool-card summaries, diff stats) MUST live in `ui/packages/app/src/vm/` as pure TypeScript functions, so it can be tested without a DOM (TDD at unit level). |
| UI-012 | Model updates from streaming events MUST be coalesced to at most one render per animation frame. |
| UI-335 | **Recent threads stay followed**: a `thread/<id>` topic MUST stay subscribed after no widget shows it any more, for the 5 most recently hidden threads (`RECENT_THREADS`; the least recently shown goes first, and a kept thread deleted from the index is released), so switching back to one of them sends no `subscribe` and renders its kept, live-updated state at once instead of waiting for a new snapshot (`TopicRefs`, `ui/packages/app/src/sdk/host.tsx`). Measured by TST-100 with 10,000 messages: switching back took 168–179 ms to the DOM (a 5.5 MB snapshot), 22–24 ms after. |

## Layout

The left column lists workspaces and, inside each, its threads; the selected thread's workspace is the current one.
The left column belongs to the frame; everything right of it is the current workspace's view (widgets, 08: its
`views.json`, else the default view): the conversation and, beside it, widgets about the current workspace.

```text
┌────────────────────┬───────────────────────────────────────────┬────────────────┐
│ + workspace        │ Thread header: title · workspace chip     │ omfp:workspace │
│ ▾ checkout-v2      │ · model · thinking · context % · state    │  checkout-v2   │
│   ● implement      │───────────────────────────────────────────│  ↪ frontend    │
│   ◐ review         │ Transcript (virtualized)                  │  ⑂ fe-v2       │
│   + thread         │   user / assistant / tool cards / notices │  ⬇ backend     │
│ ▾ scratch          │   pending interactions (approval, ask)    │  + repository  │
│   ! questions      │───────────────────────────────────────────│                │
│   + thread         │ Queue chips · Composer (/ commands, imgs) │  (more widgets)│
└────────────────────┴───────────────────────────────────────────┴────────────────┘
```

## Which-key and the leader menu

Spacemacs/Doom style: a started key sequence shows what can follow it, and `Space` is the main entry to the window's
commands. Rows here are not part of a milestone yet.

| ID | Requirement |
| --- | --- |
| UI-320 | **Which-key panel**: while a key sequence started in any mode waits for its next key (its keys start longer bindings: `g`, `z`, `]`, `Space`, an init file's `Ctrl-x` in insert mode), the window MUST show, after UI-321's delay, a panel (`which-key`, kit `WhichKey`, a popover above the mode line) listing each key that completes it: its key chip and the title of the command it runs now (the registered command of the scopes around the focused element — the frame's, a widget's `useCommand`, an init file's —, else the built-in description, else the id) with the binding's arguments; a key that only starts longer bindings shows their group (`h → help…`) or how many they are (`o → 2 bindings…`). It is built from the window's effective bindings (defaults, `[keymap]`, `.omfp/keymap.json`, init files: UI-097, UI-210, UI-262), so it lists whatever is bound now; a complete binding wins over longer ones, like the matcher. Keys are grouped by what their commands act on (`threads`, `views`, `workspace`, `files`, `help`, `move`, `command line`, `other` for the commands of widgets and init files outside these namespaces), each group in binding order; group names show when there are several. |
| UI-321 | **Timing**: the panel MUST show 300 ms after a key that leaves a sequence waiting (injectable timers, `Frame`'s `keyTimers`, for deterministic tests); a next key typed sooner never shows it. While it shows, the sequence does not time out (the 1 s timeout of UI-095 applies to sequences not shown), and the panel follows the sequence as it grows (`Space h` lists `h` and `k` at once) until a key completes it (the command runs, the panel closes) or does not continue it (the panel closes and the key acts as if typed alone). |
| UI-322 | **Cancelling**: Escape while a sequence waits MUST drop the sequence and close the panel, and do nothing else (it does not leave the composer, UI-095); a pointer press anywhere and the window losing the focus do the same. |
| UI-323 | **Accessible, motion-aware**: the panel MUST be a labelled region (`Keys after spc`) that never takes the focus (the keys keep going to the page, the mode stays), each group's name read before its key → description rows; a key whose command does not answer now (no thread selected, no current workspace, no widget registering it) is dimmed and says "(not available now)" to screen readers. Showing it announces `<keys>: N keys, Escape cancels` through the live region (UI-092). Its only motion is the popovers' pop of the motion catalogue (UI-146), so the effective motion level (UI-145, capped by the system's reduced motion) applies: none at `none`. |
| UI-324 | **Space leader menu**: `Space` in normal mode MUST open the panel at once, without UI-321's delay, on the leader's bindings in their groups (threads, views, workspace, files, help, command line, then the bindings of widgets and init files), the leader's groups (UI-326) as keys opening more. | UI-325 | **Space Space**: `Space Space` and `Space :` MUST open the `:` command line (`cmdline.open`), which `:` still opens. |
| UI-326 | **Leader map**: the flat leader keys MUST stay as they are (`Space a`, `n`, `w`, `r`, `x`, `u`, `d`, `s`, `S`, `R`, `t`, `:`), and groups add: `Space h` help (`h h` the help panel, `h k` `:describe-key`), `Space p` workspace (`p n` a new workspace, `p r` rescan it), `Space f` files (`f o` open the focused path), `Space v` views (`v v` pick a view like `g v`, `v n` / `v p` the next / previous view like `] v` / `[ v`).
