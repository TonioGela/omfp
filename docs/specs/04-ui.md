# 04 — UI (TypeScript)

The UI is a TypeScript web app (D-18): React 19 with React Aria Components (S-11), styled by our own token CSS,
bundled and tested with Bun, in the `ui/` workspace. The same bundle runs in the browser, served by the daemon
(DMN-008), and from M7 in the Tauri desktop window: same components, same state handling.

## Platforms

| | Web | Desktop (M7) |
| --- | --- | --- |
| Runtime | the release bundle (`just build-web`) in the browser | the same bundle in a Tauri 2 webview (the system webview, WebKitGTK on Linux) |
| Daemon | remote/local `omfp daemon`, which also serves the static bundle | the local daemon of the data directory, found or started in the background by `omfp desktop` (ARC-003) |
| WebSocket client | `@omfp/client` over the browser's `WebSocket` | the same |
| Token | entered once, or read from the URL fragment `#token=…` printed by `omfp daemon`; kept in `localStorage` | read from the data directory by `omfp desktop` and handed to the window at launch |

| ID | Requirement |
| --- | --- |
| UI-001 | The UI MUST have a single WebSocket transport (`@omfp/client` over the standard `WebSocket` API) for web and desktop, and it MUST pass the transport test suite against a real daemon (TST-030). |
| UI-002 | On web, after reading `#token=…` the UI MUST remove the fragment from the address bar (`history.replaceState`). |
| UI-003 | On connection loss the UI MUST show a non-blocking banner, reconnect with exponential backoff (max 10 s), and resubscribe each topic with its last `{epoch, seq}` (PRT-020). |
| UI-004 | The desktop build MUST keep the daemon reachable on `127.0.0.1` with its token, so a browser can attach to the same daemon (ARC-004). |
| UI-005 | Every `omfp desktop` invocation MUST open a new window on the shared local daemon (D-16). Window-local state (selected thread, open panels, layout, drafts) MUST stay per window; everything else comes from the daemon, so all windows show the same threads. |

## State and code structure

The UI is a Bun workspace of small packages. The protocol client has no UI dependency, so it is tested against a real
daemon and can serve other clients (scripts, agents, the desktop shell):

```text
ui/packages/
  protocol/      @omfp/protocol: protocol types and method table generated from the daemon's JSON Schemas
                 (`just gen-ts`), envelope, topics
  core/          @omfp/core: the omfp-core reducer ported to TypeScript, checked against the Rust reducer's golden
                 states (D-04)
  client/        @omfp/client: transport (WebSocket); session (hello, request/response correlation, subscriptions
                 with {epoch, seq}, reconnect with backoff, resubscribe, resync); model (connection status, index
                 with repositories, workspaces, threads and theme, per-thread ThreadState, change notifications)
  kit/           @omfp/kit: React Aria Components wrappers styled by token CSS (tokens.css, kit.css)
  app/           @omfp/app: the web app; build.ts makes the release bundle in dist/ (with the import map that
                 widgets resolve `react`, `omfp/sdk` and `omfp/kit` through, AGT-012)
    src/sdk/       the widget SDK, `omfp/sdk` (AGT-016): host, frame store (one snapshot per animation frame),
                   window store (window-local state), commands, hooks over the client model, widget hooks
    src/vm/        pure view-model functions: ThreadState / DTOs → display data (unit tested, no DOM)
    src/widgets/   the built-in `omfp:*` widgets (thin: render vm output, call the SDK), each folder written like an
                   agent widget so it can be copied (AGT-021)
    src/frame/     the frame outside the view: left column, connection banner, view switcher, layout editing
                   controls, `:` command line, safety net for pending interactions, notifications, live region
    src/view/      views: layout tree (`row`/`col`/`tabs`/`stack` of widget refs with props, the `views.json` shape
                   of 08) rendered from the widget registry (see UI-024), the widget loader and the layout edits
    src/keymap/    keymap as data: key sequence → command id, per mode
    src/theme/     built-in light/dark, user theme from the daemon, color scheme and density
    src/strings/   all UI text
```

| ID | Requirement |
| --- | --- |
| UI-010 | Thread state MUST come only from the `omfp-core` reducer (ARC-006). UI-only state (scroll position, expanded cards, composer draft) lives beside it and is never sent to the daemon. |
| UI-011 | Display logic (grouping, labels, status badges, tool-card summaries, diff stats) MUST live in `ui/packages/app/src/vm/` as pure TypeScript functions, so it can be tested without a DOM (TDD at unit level). |
| UI-012 | Model updates from streaming events MUST be coalesced to at most one render per animation frame. |

## Layout

The left column lists workspaces and, inside each, its threads; the selected thread's workspace is the current one.
The left column belongs to the frame; everything right of it is the current workspace's view (widgets, 08: its
`views.json`, else the default view): the conversation and, beside it, widgets about the current workspace.

```text
┌────────────────────┬───────────────────────────────────────────┬────────────────┐
│ + workspace        │ Thread header: title · repo chips         │ omfp:workspace │
│ ▾ checkout-v2      │ · model · thinking · context % · state    │  checkout-v2   │
│   ● implement      │───────────────────────────────────────────│  ↪ frontend    │
│   ◐ review         │ Transcript (virtualized)                  │  ⑂ fe-v2       │
│   + thread         │   user / assistant / tool cards / notices │  ⬇ backend     │
│ ▾ scratch          │   pending interactions (approval, ask)    │  + repository  │
│   ! questions      │───────────────────────────────────────────│                │
│   + thread         │ Queue chips · Composer (/ commands, imgs) │  (more widgets)│
└────────────────────┴───────────────────────────────────────────┴────────────────┘
```

| ID | Requirement |
| --- | --- |
| UI-020 | The left column MUST list every workspace as a section (name, the current one highlighted, a menu with rename and remove) with its threads (process and attention state — running, awaiting input, failed, idle, unread — and title), and nothing else: no grouping or filter controls, no settings. Every thread row and every workspace header has a delete button, shown on hover and on keyboard focus (also `dd` on the focused row), which asks for confirmation (UI-026 for threads, DMN-028 for workspaces: removing a workspace with threads offers to delete them too, and the dialog says its folder is deleted while linked projects are kept). |
| UI-021 | Threads awaiting input MUST be reachable with one keyboard shortcut ("next thread needing attention"). |
| UI-022 | One full-text filter field at the top of the left column (also focused by `/`) filters threads: a thread matches when its title, workspace name, repository names **or its conversation text** contain the query (case-insensitive; the conversation part comes from `threads.search`, DMN-076); workspaces without matching threads are hidden while filtering. Each workspace section can be collapsed (chevron, or `za` on the section); the collapsed set is window-local and survives reloads. There are no other grouping or filtering modes. |
| UI-023 | Each workspace section ends with "+ thread", which opens a **draft thread** in that workspace at once: selected, composer focused, no dialog and no title (DMN-073). The daemon thread is created only when the first message is sent (`threads.create { workspace, prompt }`); leaving an empty draft discards it. "+ workspace" at the top of the column is an inline field taking a **name or a path**: input starting with `/` or `~` is a path, with completion as in DMN-021, and Enter creates a new workspace named after the folder's name (made unique) holding a link to that folder (`workspaces.create { link }`); any other input is the workspace's name (optional: empty gets the placeholder name). Enter then opens a draft thread in the new workspace. With no workspace yet, the column shows only that field, focused, with a one-line hint. Repositories are added from the `omfp:workspace` widget or by asking the agent. The header offers rename; asking the agent to rename the thread works through its `set_thread_title` tool. |
| UI-024 | Panels MUST go through a registry (kind, typed content, placement: side, bottom, main, floating) rather than a fixed layout, so new panel kinds — including views published by agents ([08](08-agent-control.md)) — fit without restructuring the shell. |
| UI-025 | The `omfp:workspace` widget MUST show the current workspace: name (editable), folder path (copyable), and every repository discovered in it with kind (link and target, worktree and its main repository, clone), branch, dirty state and ahead/behind, updated live as the agent adds or removes repos (the daemon rescans on its own, DMN-023; `:rescan` forces a rescan of the current workspace); one "add repository" control with a Link / Clone switch (the link's path field with suggestions and completion as in DMN-021), remove for every kind (DMN-025, with a confirmation for anything but a link; worktrees are only listed and removed, the agent creates them), and a badge when the same repository is in another workspace with live threads (DMN-027). |
| UI-026 | The thread header MUST offer archive (unarchive when archived) and delete; delete asks for confirmation in a dialog saying the thread's history is removed and its workspace is kept. Archived threads are hidden except for a collapsed "Archived (N)" row at the end of their workspace section, which lists them so they can be reopened, unarchived or deleted. Archiving or deleting the selected thread clears the selection and drops its draft. |

### Tool cards

omp sends raw events (`tool_execution_start/update/end` with arguments and result); cards are our job.

| Tool | Card |
| --- | --- |
| any (fallback) | name, one-line argument summary, status, duration; expandable pretty JSON args and text result |
| `bash` | command, streaming output (ANSI → HTML), exit code, and the workspace it ran in when not the cwd |
| `read` | path and line range, result collapsed |
| `edit` / `write` | file path (relative to its workspace, with the workspace chip) and a diff view |
| `grep` / `glob` / `find` / `ast_grep` | query and result list with file links |
| `task` | subagent name and task, live progress, link to the subagent panel |
| `todo` | checklist |
| `web_search` / `fetch` | query, link list |
| `ask` | questions with the given answers |

| ID | Requirement |
| --- | --- |
| UI-050 | Every tool MUST render through the fallback card when no specialized renderer exists; specialized renderers are added one at a time, each with tests (TST-020). |
| UI-051 | Tool argument/result shapes for specialized cards MUST be captured as fixtures from the pinned omp (recorded by the contract tests, TST-012) and re-checked on every omp upgrade. |
| UI-052 | Cards MUST be collapsible; failed tools (`isError`) MUST be visually distinct and expanded by default. |

### Composer and queue

| ID | Requirement |
| --- | --- |
| UI-060 | The composer MUST support multi-line input, image paste/drop, and `/` command completion from `thread.commands` (kept fresh by `available_commands_update`). |
| UI-061 | While the thread is `Busy`, sending MUST queue the message as follow-up by default; a modifier sends it as steer. The choice MUST be visible on the send button. |
| UI-062 | Queue chips MUST be rendered only from `queue_update` snapshots; remove and promote MUST wait for the daemon's confirmation (`removed`/`promoted`) before changing the chip. |
| UI-063 | Abort (Esc in the composer) MUST call `thread.abort` and put the returned steering and follow-up texts back in the composer draft. `Ctrl-C` in the composer (in insert mode too; it never copies there, while copying a selection elsewhere is unaffected) clears a non-empty draft (text and images), keeping it in memory so `u` in normal mode restores the last cleared draft of the thread; on an empty draft, or pressed again within 1 s, it aborts with `thread.abort`, which stops the running turn and drops the queued steering and follow-up messages, and — unlike Esc — the returned texts are **not** put back in the composer. After the first press a short hint ("Ctrl-C again to abort") shows while the thread is busy or has queued messages. Both are keymap commands (UI-095). |
| UI-064 | Drafts MUST be kept per thread across thread switches and reconnects (local only). |

## Views and layout editing (M4)

| ID | Requirement |
| --- | --- |
| UI-100 | The frame MUST render the left column (UI-020..023) itself, outside any view; right of it, the view of the current workspace (the selected thread's, else the draft thread's) from its `views/<id>` topic (PRT-040), which the frame follows only while that workspace is current; with no current workspace, no manifest or before the topic answers, the default view (AGT-010). |
| UI-101 | The view switcher in the frame bar MUST list the current workspace's views by title, in id order, and show the chosen one in this window only (window-local); `:view <id>` does the same. When the chosen view no longer exists, the window shows the manifest's default view. |
| UI-102 | An invalid manifest (AGT-011) MUST show a banner (`view-error`) with the daemon's error above the default view; it goes away when a valid manifest arrives. |
| UI-103 | **Layout editing**: "Edit layout" in the frame bar (and `:layout`) toggles this window's edit mode. In edit mode every widget of the view gets a toolbar with its reference, a **Move** menu (before or after any other widget of the view, or at the end of any container) and **Hide** (removes it; a container left without children goes too; the view's last widget cannot be hidden), and a splitter between the cells of each `row` and `col` resizes them with the pointer or with the arrow keys (5 % steps). Every change is computed on the manifest by pure functions (unit tested) and written with `views.set`; the first change in a workspace without `views.json` writes the default view with that change. The window then renders the manifest the daemon pushes. Edit mode needs a current workspace; while its views topic has not answered, or while its `views.json` is invalid (UI-102), changes are refused with an error (the file is never overwritten). A cell added to a container with `sizes` weighs the mean of its siblings (a cell moved within its container keeps its weight); a resized cell keeps at least 5 % of its container. |
| UI-104 | **Widget picker**: in edit mode, "Add widget" opens a dialog listing the built-in widgets, the workspace's widgets (`./widgets/<name>`) and the user library's (`user:<name>`); picking one adds it at the end of the view's root container (a root widget becomes a `row` of both) and writes the manifest (UI-103). |
| UI-105 | **Widget loader**: workspace and user widgets MUST be imported with the browser's `import()` from `<widgetBase>/<workspace id \| user>/<name>/<version>/<entry>` (DMN-084), showing a placeholder while loading; a new `version` imports that widget again and re-renders it alone, other widgets untouched (AGT-013). A compile error (the module's `compileError`), a failed import, a missing entry or default export, and a render error show in the widget's place (`widget-error`, with the file, line and column when known, AGT-014). |
| UI-106 | `:widget copy <reference> [<name>]` MUST copy a built-in or user widget into the current workspace (`widgets.copy`, DMN-087), announce the new `./widgets/<name>` and report failures in the frame's error list. |

## Rendering details

| ID | Requirement |
| --- | --- |
| UI-090 | Code highlighting MUST work on both platforms. The library is chosen by spike S-03 with a bundle size budget (target: total gzipped bundle ≤ 3 MiB). |
| UI-091 | Styling uses plain CSS driven only by design tokens (CSS custom properties named after Material 3 roles: `--omfp-primary`, `--omfp-on-primary`, `--omfp-surface`, `--omfp-surface-container`, `--omfp-outline`, …, plus radius, spacing, font and density tokens); the shell, the kit and widgets never hard-code colors. The theme is **global** to omfp and **kept by the daemon** (a setting, served at `/theme.css`, change pushed to every window), because the daemon may be remote: built-in light and dark follow `prefers-color-scheme` with a manual override; a user theme (CSS overriding any token) replaces them. It can be set with `theme.set`, by `omfp theme set <file>` (local or `--daemon <url>`), by a theme file on the daemon host (`$XDG_CONFIG_HOME/omfp/theme.css`, watched), and by the desktop app (M7), which watches the same path **on the client machine** and pushes it — so **matugen** (template in `contrib/matugen/`) recolors every window live even with a remote daemon. |
| UI-092 | All interactive elements MUST be keyboard reachable, dialogs MUST trap focus, and status changes MUST be announced through an ARIA live region. |
| UI-093 | From M3 (D-18) the UI is TypeScript with React 19 (S-11) and React Aria Components for behaviour and accessibility (UI-092), styled by our own token CSS; a thin kit (`omfp/kit`: card, button, tabs, table, list, progress, log, diff, markdown, …) wraps them for the shell and for widgets. |
| UI-094 | Fonts are tokens too (`--omfp-font-prose`, `--omfp-font-ui`, `--omfp-font-code`), defaulting to the system families (`ui-serif`, `system-ui`, `ui-monospace` with fallbacks): serif only for message prose (transcript text, Markdown), sans for the interface, monospace only for code (code blocks, inline code, tool commands and output). Choosing other fonts is left to the theme for now. The layout is dense by default, with a density token (compact / normal) settable at run time. Size tokens are in `rem`, so the root font size (`[ui] font_size`, default 16px, UI-097) scales all of them. |
| UI-095 | Keyboard handling MUST go through one keymap (data: key sequence → command id, per mode), so bindings can be made configurable later. Default bindings are vim-style: `j`/`k` move between threads or messages, `gg`/`G` top/bottom, `Ctrl-d`/`Ctrl-u` half pages, `/` search, `i` focuses the composer, `Esc` leaves it, `Ctrl-C` clears the composer then aborts and `u` restores the last cleared draft (UI-063); `:` opens a command line that is also the command palette (`:new`, `:archive`, `:rescan` (the current workspace, DMN-023), `:theme dark`, … with completion); `Space` is the leader for actions (`Space n` a draft thread in the current workspace, `Space w` the "+ workspace" field); `dd` deletes and `za` collapses the focused row or workspace section of the left column. The transcript handles PageUp/PageDown/Home/End itself (WebKitGTK does not scroll a focused container, S-11). Modal (Helix-style) editing inside the composer is out of scope for M3. |
| UI-096 | When a thread starts needing the user (approval, `ask`, failure) or finishes a turn and the window does not have focus, the UI MUST show a system notification (Notification API, permission asked on a user gesture); clicking it focuses the window on that thread. Nothing is shown while the window has focus. |
| UI-097 | UI settings come from the daemon (DMN-009): `[ui]` `density` (compact / normal), `font_size` (root font size in px, 10–28, default 16, set inline on `<html>`), `notifications` (background / always / never), `fonts` (`prose`, `ui`, `code` overriding the font tokens), and `[keymap]` entries (key sequence → command id) that override the default bindings one by one. Changes apply live in every window; `:set <key>=<value>` changes a setting through `settings.set`. |
