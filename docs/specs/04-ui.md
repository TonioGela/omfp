# 04 — UI (TypeScript)

The UI is a TypeScript web app (D-18): React 19 with React Aria Components (S-11), styled by our own token CSS,
bundled and tested with Bun, in the `ui/` workspace. The same bundle runs in the browser, served by the daemon
(DMN-008), and from M7 in the Tauri desktop window: same components, same state handling.

## Platforms

| | Web | Desktop (M7) |
| --- | --- | --- |
| Runtime | the release bundle (`just build-web`) in the browser | the same bundle in a Tauri 2 webview (the system webview, WebKitGTK on Linux) |
| Daemon | remote/local `omfp daemon`, which also serves the static bundle | the local daemon of the data directory, found or started in the background by `omfp desktop` (ARC-003) |
| WebSocket client | `@omfp/client` over the browser's `WebSocket` | the same |

## State and code structure

The UI is a Bun workspace of small packages. The protocol client has no UI dependency, so it is tested against a real
daemon and can serve other clients (scripts, agents, the desktop shell):

```text
ui/packages/
  protocol/      @omfp/protocol: protocol types and method table generated from the daemon's JSON Schemas
                 (`just gen-ts`), envelope, topics
  core/          @omfp/core: the omfp-core reducer ported to TypeScript, checked against the Rust reducer's golden
                 states (D-04)
  client/        @omfp/client: transport (WebSocket); session (hello, request/response correlation, subscriptions
                 with {epoch, seq}, reconnect with backoff, resubscribe, resync); model (connection status, index
                 with repositories, workspaces, threads and theme, per-thread ThreadState, change notifications)
  kit/           @omfp/kit: React Aria Components wrappers styled by token CSS (tokens.css, kit.css)
  app/           @omfp/app: the web app; build.ts makes the release bundle in dist/ (with the import map that
                 widgets resolve `react`, `omfp/sdk` and `omfp/kit` through, AGT-012)
    src/sdk/       the widget SDK, `omfp/sdk` (AGT-016): host, frame store (one snapshot per animation frame),
                   window store (window-local state), commands, hooks over the client model, widget hooks
    src/vm/        pure view-model functions: ThreadState / DTOs → display data (unit tested, no DOM)
    src/widgets/   the built-in `omfp:*` widgets (thin: render vm output, call the SDK), each folder written like an
                   agent widget so it can be copied (AGT-021)
    src/frame/     the frame outside the view: left column, connection banner, view switcher, layout editing
                   controls, `:` command line, safety net for pending interactions, notifications, live region
    src/view/      views: layout tree (`row`/`col`/`tabs`/`stack` of widget refs with props, the `views.json` shape
                   of 08) rendered from the widget registry (see UI-024), the widget loader and the layout edits
    src/keymap/    keymap as data: key sequence → command id, per mode
    src/theme/     built-in light/dark, user theme from the daemon, color scheme and density
    src/strings/   all UI text
```

| ID | Requirement |
| --- | --- |
| UI-010 | Thread state MUST come only from the `omfp-core` reducer (ARC-006). UI-only state (scroll position, expanded cards, composer draft) lives beside it and is never sent to the daemon. |
| UI-011 | Display logic (grouping, labels, status badges, tool-card summaries, diff stats) MUST live in `ui/packages/app/src/vm/` as pure TypeScript functions, so it can be tested without a DOM (TDD at unit level). |
| UI-012 | Model updates from streaming events MUST be coalesced to at most one render per animation frame. |

## Layout

The left column lists workspaces and, inside each, its threads; the selected thread's workspace is the current one.
The left column belongs to the frame; everything right of it is the current workspace's view (widgets, 08: its
`views.json`, else the default view): the conversation and, beside it, widgets about the current workspace.

```text
┌────────────────────┬───────────────────────────────────────────┬────────────────┐
│ + workspace        │ Thread header: title · repo chips         │ omfp:workspace │
│ ▾ checkout-v2      │ · model · thinking · context % · state    │  checkout-v2   │
│   ● implement      │───────────────────────────────────────────│  ↪ frontend    │
│   ◐ review         │ Transcript (virtualized)                  │  ⑂ fe-v2       │
│   + thread         │   user / assistant / tool cards / notices │  ⬇ backend     │
│ ▾ scratch          │   pending interactions (approval, ask)    │  + repository  │
│   ! questions      │───────────────────────────────────────────│                │
│   + thread         │ Queue chips · Composer (/ commands, imgs) │  (more widgets)│
└────────────────────┴───────────────────────────────────────────┴────────────────┘
```

| ID | Requirement |
| --- | --- |
| UI-020 | The left column MUST list every workspace as a section (name, the current one highlighted, a menu with rename and remove) with its threads (process and attention state — running, awaiting input, failed, idle, unread — and title), and nothing else: no grouping or filter controls, no settings. Every thread row and every workspace header has a delete button, shown on hover and on keyboard focus (also `dd` on the focused row), which asks for confirmation (UI-026 for threads, DMN-028 for workspaces: removing a workspace with threads offers to delete them too, and the dialog says its folder is deleted while linked projects are kept). |
| UI-021 | Threads awaiting input MUST be reachable with one keyboard shortcut ("next thread needing attention"). |
| UI-022 | One full-text filter field at the top of the left column (also focused by `/`) filters threads: a thread matches when its title, workspace name, repository names **or its conversation text** contain the query (case-insensitive; the conversation part comes from `threads.search`, DMN-076); workspaces without matching threads are hidden while filtering. Each workspace section can be collapsed (chevron, or `za` on the section); the collapsed set is window-local and survives reloads. There are no other grouping or filtering modes. |
| UI-023 | Each workspace section ends with "+ thread", which opens a **draft thread** in that workspace at once: selected, composer focused, no dialog and no title (DMN-073). The daemon thread is created only when the first message is sent (`threads.create { workspace, prompt }`); leaving an empty draft discards it. Enter then opens a draft thread in the new workspace. With no workspace yet, the column shows only that field, focused, with a one-line hint. | UI-026 | The thread header MUST offer archive (unarchive when archived) and delete; delete asks for confirmation in a dialog saying the thread's history is removed and its workspace is kept. Archived threads are hidden except for a collapsed "Archived (N)" row at the end of their workspace section, which lists them so they can be reopened, unarchived or deleted. Archiving or deleting the selected thread clears the selection and drops its draft. |

phone does; the splitters resize the view for this window only.

### Tool cards

omp sends raw events (`tool_execution_start/update/end` with arguments and result); cards are our job.

| Tool | Card |
| --- | --- |
| any (fallback) | name, one-line argument summary, status, duration; expandable pretty JSON args and text result |
| `bash` | command, streaming output (ANSI → HTML), exit code, and the workspace it ran in when not the cwd |
| `read` | path and line range, result collapsed; the path opens the file at that line (UI-116) |
| `edit` / `write` | file path (relative to its repository, with the repository chip, when it lies in one of the workspace's repositories), which opens the file against `HEAD` (UI-116); `edit` a diff view, `write` the first lines of the content, expandable (UI-053) |
| `grep` / `glob` / `find` / `ast_grep` | query and result list (each `grep`/`glob` file path opens the file, UI-116) |
| `task` | subagent name and task, live progress (the link to a subagent panel comes with that panel, M8) |
| `todo` | checklist |
| `web_search` / `fetch` | query, link list |
| `ask` | questions with the given answers |

A specialized card's header shows its subject (command, path, query or pattern) in place of those arguments: its
argument summary leaves them out, along with what the body shows (a `write`'s content, an `edit`'s input), and shows
no partial argument text while the model writes them.

## Files (M5c)

A file viewer for quick edits (00: not an IDE), built on CodeMirror 6 (spike S-13): the built-in `omfp:file` widget,
opened from paths anywhere in the window. The editor, vim, the merge view and each language are chunks of the bundle
loaded on first use.

| ID | Requirement |
| --- | --- |
| UI-110 | **`omfp:file { path, line?, diff? }`** (a built-in widget, copyable like the others) MUST show the workspace file `path` (`workspaces.read_file`, DMN-089) read-only in CodeMirror: line numbers, highlighting by the file's language, the cursor on `line` scrolled into view, a notice when the daemon cut the file (it then stays read-only), images rendered, binaries only named with their size. The tab polls the file (`knownHash`, every 2 s while shown, and when `workspace/<id>` publishes a new status) and reloads it in place when it changed and the view has no unsaved change; with unsaved changes it shows that the file changed on disk. |
| UI-111 | **Editing**: `i` in the read-only view (or the Edit button) switches to editing with vim bindings (`@replit/codemirror-vim`) in insert mode; `:w` or Ctrl-S saves with `workspaces.write_file { expectedHash }` (the hash the text was based on, DMN-090), then the view stays in editing with the new hash; `:q` and the Done button go back to read-only, unless there are unsaved changes (the view then says so; `:q!` drops them and reloads the file). The editor owns Esc while it has the focus: Esc goes to vim (insert → normal, cancel a pending command), and only in normal mode with nothing pending does it leave the editor, focusing the tab's panel without losing the window's focus; the app keymap treats the editor as a text field (UI-095). |
| UI-112 | While the editor has the focus, the mode line (UI-098) MUST show vim's mode (`NORMAL`, `INSERT`, `VISUAL`, `REPLACE`, from `vim-mode-change`) instead of the keymap's. |
| UI-113 | **Conflict**: a save refused with `conflict` (the file changed on disk since it was read) MUST NOT lose or overwrite anything: the view shows a merge view of the file on disk against the user's text, with "Keep editing" (back to the user's text, still unsaved), "Overwrite" (saves the user's text over the file now on disk, with that file's hash) and "Discard mine" (reloads the file). |
| UI-114 | **Diff**: with `diff: true` the view shows the whole file against its `HEAD` text (DMN-089) with `@codemirror/merge`, unified by default, with a side-by-side toggle; a file `HEAD` lacks shows as all added, a file outside any repository says so. The toggle and the read-only/edit views keep the file loaded. |
| UI-115 | **Opening**: `openFile(path, { line?, diff? })` (SDK, AGT-027) opens a file in this window: in the view's `tabs` container with `"id": "main"`, as a closable tab after the container's own children (in the default view, after the pinned chat tab), selected; opening a path that is already open selects its tab and applies `line` and `diff`. The open tabs and the selected one are window-local per workspace (`localStorage`), never written to `views.json`. In a view without a `main` slot, the open files are the tabs of a panel floating over the view, with the same tab behaviour (selected tab, closing one selects its neighbour, Esc or the close button closes the selected one); the panel moves by its grip and resizes by its corner (pointer, or arrow keys on the focused grip or corner, Shift for bigger steps), minimises to its bar, and its place, size and minimised state are window-local too (`localStorage`). |

Relative paths are resolved by the daemon against the workspace folder, then its repositories (DMN-089). `g f` (keymap command `file.open`) opens the path of the focused element or of its nearest ancestor that carries one (`data-omfp-path`, with `data-omfp-line` / `data-omfp-diff`), e.g. a focused tool card. | UI-117 | **Bare and partial names**: a file whose path does not exist as given (`theme.ts`, `src/theme.ts`, a path relative to another folder) is looked up with `workspaces.find_file` (DMN-092, with the selected thread so files its tool cards name rank first) by the `omfp:file` view showing it (`useMissingFile`, AGT-027): one candidate opens directly in place of the missing path's tab (keeping `line` and `diff`; a tab already showing that file takes them instead), several open the **file picker** in the command line's style at the bottom of the window — an input that filters the candidates, the best one highlighted, the arrows moving through them, Enter (or a click) opening the highlighted one in place of the missing path's tab, Esc or leaving the line cancelling the opening (the missing path's tab closes) —, none leaves the view saying the file does not exist. |

## Rendering details

| ID | Requirement |
| --- | --- |
| UI-090 | Code highlighting MUST work on both platforms. The library is chosen by spike S-03 with a bundle size budget (target: total gzipped bundle ≤ 3 MiB): highlight.js grammars through lowlight, each loaded on first use, in Markdown code fences, diffs and tool results whose language is known (from the fence or the file name). Token colors come only from the theme's role tokens (`hljs-*` classes in kit.css), so light, dark and user themes recolor code. |
| UI-091 | Styling uses plain CSS driven only by design tokens (CSS custom properties named after Material 3 roles: `--omfp-primary`, `--omfp-on-primary`, `--omfp-surface`, `--omfp-surface-container`, `--omfp-outline`, …, plus radius, spacing, font and density tokens); the shell, the kit and widgets never hard-code colors. The theme is **global** to omfp and **kept by the daemon** (a setting, served at `/theme.css`, change pushed to every window), because the daemon may be remote: built-in light and dark follow `prefers-color-scheme` with a manual override; a user theme (CSS overriding any token) replaces them. It can be set with `theme.set`, by `omfp theme set <file>` (local or `--daemon <url>`), by a theme file on the daemon host (`$XDG_CONFIG_HOME/omfp/theme.css`, watched), and by the desktop app (M7), which watches the same path **on the client machine** and pushes it — so **matugen** (template in `contrib/matugen/`) recolors every window live even with a remote daemon. The token list, the built-in palette and the color rules are in [09](09-design.md) (UI-125..UI-140). |
| UI-092 | All interactive elements MUST be keyboard reachable, dialogs MUST trap focus, and status changes MUST be announced through an ARIA live region. |
| UI-093 | From M3 (D-18) the UI is TypeScript with React 19 (S-11) and React Aria Components for behaviour and accessibility (UI-092), styled by our own token CSS; a thin kit (`omfp/kit`: card, button, tabs, table, list, progress, log, diff, markdown, …) wraps them for the shell and for widgets. |
| UI-094 | Fonts are tokens too (`--omfp-font-prose`, `--omfp-font-ui`, `--omfp-font-code`): serif only for message prose (transcript text, Markdown), monospace for the interface chrome and for code; the bundled families, fallbacks and the type scale are in [09](09-design.md) (UI-121, UI-141..UI-144). The layout is dense by default, with a density token (compact / normal) settable at run time. Size tokens are in `rem`, so the root font size (`[ui] font_size`, default 17 px, UI-097) scales all of them. |
| UI-095 | Keyboard handling MUST go through one keymap (data: key sequence → command id, per mode), so bindings can be made configurable later. Default bindings are vim-style: `j`/`k` move between threads or messages, `gg`/`G` top/bottom, `Ctrl-d`/`Ctrl-u` half pages, `/` search, `i` focuses the composer, `Esc` leaves it, `Ctrl-C` clears the composer then aborts and `u` restores the last cleared draft (UI-063); `:` opens a command line that is also the command palette (`:new`, `:archive`, `:rescan` (the current workspace, DMN-023), `:theme dark`, … with completion); `Space` is the leader for actions (`Space n` a draft thread in the current workspace, `Space w` the "+ workspace" field); `dd` deletes and `za` collapses the focused row or workspace section of the left column. `g n` opens the newest mode-line notice (UI-192). `?` (also `:help`) opens the help panel listing every binding and command (UI-198). The transcript handles PageUp/PageDown/Home/End itself (WebKitGTK does not scroll a focused container, S-11). Modal (Helix-style) editing inside the composer is out of scope for M3. |
| UI-096 | When a thread starts needing the user (approval, `ask`, failure) or finishes a turn and the window does not have focus, the UI MUST show a system notification (Notification API, permission asked on a user gesture); clicking it focuses the window on that thread. While the window has focus no system notification is shown (unless `[ui] notifications = "always"`, UI-097): the same event is a mode-line notice instead (UI-192). Thread events, agents' `omfp_notify` (UI-215) and widgets' `notify` (UI-194) go through one notice entry point (`host.notices.notify`). |
| UI-097 | UI settings come from the daemon (DMN-009): `[ui]` `density` (compact / normal), `font_size` (root font size in px, 10–28, default 17, set inline on `<html>`), `motion` (full / reduced / none, UI-145), `notifications` (background / always / never: system notifications only without focus, also with focus, or no system notification and no mode-line notice, UI-096, UI-192), `fonts` (`prose`, `ui`, `code` overriding the font tokens), and `[keymap]` entries (key sequence → command id) that override the default bindings one by one. Changes apply live in every window; `:set <key>=<value>` changes a setting through `settings.set`. |
| UI-098 | The frame MUST show the keymap mode (UI-095) — `NORMAL`, `INSERT` or `COMMAND` — at the bottom left of the view area, right of the left column, like vim's mode line (vim's own mode while the file editor has the focus, UI-112), and the composer MUST have a distinct border (theme tokens only, UI-091) while in insert mode. A mode change caused by a key (`i`, `Esc`, `:`, …) is announced through the live region (UI-092); one caused by the mouse is not. |
| UI-198 | **Help panel**: `?` in normal mode or `:help` (command `help.open`, rebindable in `[keymap]`) MUST open a modal border box titled `help` on its top border (UI-187, the closing keys at its end) listing every effective binding — the defaults merged with the daemon's `[keymap]` entries, live, including bindings to commands widgets register with `useCommand` — grouped by where they apply, each row its key chips (UI-148) and the description of the command it runs there (the registered command's title in that scope, else the built-in description every default binding has): `normal`, `insert · composer` (plus the composer's own `enter`, `alt+enter`, `shift+enter`, `tab`), `transcript` (its `nav.*` moves and its own PageUp/PageDown/Home/End), `command line` (plus `tab`, `up`/`down`, `enter`, `esc`), `file editor · vim` (a note that vim's keys apply, `esc`, `:w`/`ctrl+s`, `:q`, `:q!`), then `commands`: every registered `:` command by its names (aliases, else id) with its argument values and description. Escape, a click outside, or the key that opened it while the filter is empty closes it, and the focus goes back where it was. At most `min(46rem, 92%)` wide and `min(44rem, 100vh − 2 × s4)` tall, rows at `fs-xs` in the code family. |
| UI-210 | **Workspace keymap**: while a workspace is the window's current one (UI-100), the bindings of its `.omfp/keymap.json` (its `views/<id>` topic, DMN-121) MUST apply over the defaults and the daemon's `[keymap]` entries, one by one like those (UI-097: an entry replaces the binding with the same mode and keys, `""` removes it, any other is added; keys normalized), so the workspace wins over the global entries, which win over the defaults; a binding's `args` reach the command. Switching to a thread of another workspace swaps them for that workspace's, live like every topic change. |
| UI-211 | The help panel (UI-198) MUST list the current workspace's bindings (UI-210) in a group of their own, `workspace`, first: one row per command and arguments, its key chips, the arguments, and the description of the command in that mode (the mode in parentheses for `insert` and `command line`); the other groups show the defaults with the `[keymap]` entries the workspace does not replace or remove. |
| UI-212 | An invalid `.omfp/keymap.json` MUST show a banner (`keymap-error`) with the daemon's error while its last valid bindings stay in force (DMN-121); it goes away when a valid file arrives. |
| UI-192 | While the window has focus, a thread other than the selected one that starts needing the user, fails or finishes a turn MUST show a **notice in the mode line** (UI-167, look UI-193), never over the content: `◆`, the thread title and what happened (`needs you`, `failed`, `finished its turn`) in the tone's color, `+n` when more notices wait (the newest shows), and the key chip of `notice.open` (`g n` by default, also `:notice`).
